Greedy Algorithms

Make the choice that looks best right now, never look back, and hope it adds up to the best overall. When it works, greedy gives the simplest and fastest solutions there are. The skill is knowing which choice to make and proving it’s safe — this page teaches both.

01 The basics

What is a greedy algorithm?

A greedy algorithm builds a solution step by step. At every step it takes the option that is locally best by some rule, commits to it, and never undoes it.

  • No backtracking, no table of sub-results — usually just a sort and a loop.
  • Typical cost: O(n log n) for the sort, O(n) for the scan.
  • It’s only correct for problems with the right structure — and wrong answers look perfectly plausible.

Two properties make greedy correct

  • Greedy-choice property: some optimal solution starts with the greedy choice. Making it never rules out the optimum.
  • Optimal substructure: after the choice, what remains is a smaller copy of the same problem, and its optimal solution combines with the choice into an optimal whole.

Dynamic programming needs only the second property; greedy needs both — which is why it’s faster but rarer.

02 How to know (and prove) greedy works

Interviewers rarely want a formal proof, but they do want a convincing why. These three tools cover almost everything.

🔄

Exchange argument

Take any optimal solution that differs from greedy. Show you can swap one of its choices for the greedy one without making it worse. Repeat until it is the greedy solution — so greedy is optimal too.

🏃

Greedy stays ahead

Show that after every step, greedy’s partial solution is at least as good as any other’s (e.g. it has finished by an earlier time). If it’s never behind, it can’t lose at the end.

🔍

Hunt for a counterexample

Before coding, try 3–4 tiny inputs designed to break your rule: a long item first, a short item in the middle, ties. If you find one, switch rule or switch to DP.

Worked proof — interval scheduling (pick the most non-overlapping intervals)

  1. Rule: sort by end time; repeatedly take the interval that ends first and doesn’t overlap the last one taken.
  2. Exchange: let O be an optimal answer and g the first interval greedy takes. If O’s first interval o₁ ≠ g, replace o₁ with g. Since g ends no later than o₁, g overlaps nothing that o₁ didn’t — O stays valid and the same size.
  3. Induction: after fixing the first choice, the rest is the same problem on the intervals that start after g ends. Repeat the argument → greedy’s answer has the same size as O.
  4. Why not “earliest start” or “shortest”? One long interval that starts first, or one short interval that overlaps two others, breaks them. The visualizer shows both.

03 The common greedy patterns

Most greedy questions are one of these shapes. Spot the shape and the choice rule follows.

1 · Sort by end time (intervals)

Max non-overlapping intervals, min removals, min arrows, activity selection. The interval that ends first leaves the most room.

3 · Farthest reach (jump games)

Track the furthest index you can reach so far. If the current index is beyond it, you’re stuck. For minimum jumps, count “levels” like BFS.

    reach = max(reach, i + a[i]);
}

4 · Reset when it goes negative (running balance)

5 · Heap: always take the best available

Meeting rooms, IPO, connect ropes, Huffman coding, Dijkstra. When the best choice changes as you go, keep candidates in a priority queue.

// min cost to connect ropes: always join the two shortest
priority_queue<long long, vector<long long>, greater<>> pq(r.begin(), r.end());
long long cost = 0;
while (pq.size() > 1) {
    long long a = pq.top(); pq.pop();
    long long b = pq.top(); pq.pop();
    cost += a + b; pq.push(a + b);
}
// min cost to connect ropes: always join the two shortest
PriorityQueue<Long> pq = new PriorityQueue<>();
for (int x : r) pq.add((long) x);
long cost = 0;
while (pq.size() > 1) {
    long a = pq.poll(), b = pq.poll();
    cost += a + b; pq.add(a + b);
}
# min cost to connect ropes: always join the two shortest
import heapq
heapq.heapify(r)
cost = 0
while len(r) > 1:
    a, b = heapq.heappop(r), heapq.heappop(r)
    cost += a + b
    heapq.heappush(r, a + b)

05 Tips & tricks to learn it properly

🧭

Name the choice rule

Say it in one sentence: “always take the interval that ends first”. If you can’t, you don’t have a greedy algorithm yet.

🗂️

Sorting is step one

90% of greedy solutions begin by sorting. The real question is by which key: start, end, ratio, deadline, size?

💣

Try to break it first

Spend two minutes on tiny counterexamples before coding. A wrong greedy passes the sample and fails hidden tests.

🔄

Use the exchange argument

“If an optimal answer didn’t pick X, swapping it in doesn’t hurt.” This one sentence convinces most interviewers.

🎒

0/1 vs fractional

Can you take part of an item? Greedy by ratio. All or nothing? That’s DP. Same story for coin change.

🔁

Think from both ends

Some problems need two passes (Candy, trapping rain water): one left-to-right, one right-to-left, then combine.

⛰️

Track a running best

Farthest reach, min price so far, current balance. One variable updated per step often replaces a whole DP table.

📦

Heap when choices evolve

If the “best available” option changes as you go (new items unlock, old ones expire), keep them in a priority queue.

🤝

Ties and comparators

Decide what happens on ties, and use Integer.compare instead of a - b to avoid overflow.

🔢

Counting beats simulating

Task scheduler, hand of straights: count frequencies first; a formula or a sorted map is often enough.

📐

Touching intervals

Does [1,2] overlap [2,3]? Read the problem — it decides >= vs >.

🧠

Know the famous ones

Dijkstra, Prim/Kruskal (MST) and Huffman coding are greedy too. Recognising the family helps you trust the approach.

Common mistakes checklist

  • Using greedy where only DP works (0/1 knapsack, arbitrary coin systems).
  • Sorting by the wrong key (start instead of end for max non-overlapping).
  • Off-by-one on touching intervals (> vs >=).
  • Overflow in comparators (a[1] - b[1] with large values).
  • Forgetting the global feasibility check (gas station’s total < 0).
  • Only one pass when the constraint looks both ways (Candy).
  • Trusting a rule because it passed the examples — prove it or break it.
